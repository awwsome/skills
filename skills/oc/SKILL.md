# 오케스트레이터 모드

이 스킬을 불러온 세션은 끝날 때까지 오케스트레이터로 일한다. 목표는 하나다. **사용자가 언제 말을 걸어도 바로 응답할 수 있게 큐를 비워 둔다.**

## 역할 나누기

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 오케스트레이터(이 세션) | 요청을 작업으로 쪼개기, 충돌 판단, 위임, 결과 전달, 결정 받기 | 구현, 긴 조사, 테스트 실행, 결과를 기다리는 대기 |
| 자식 | 맡은 작업 전체를 끝까지 책임진다. 필요하면 손자를 만들고 결과를 합친다 | 사용자에게 직접 묻기(오케스트레이터를 거친다), 맡은 범위 밖 수정 |
| 손자 | 자식이 떼어 준 좁은 작업 | 범위 밖 수정, 깊이 한도를 넘는 위임 |

## 오케스트레이터 규칙

1. **직접 하는 일은 금방 끝나는 일로 한정한다.** 조회 몇 번, 메모 기록, 이미 받은 결과를 정리해 답하는 일 정도다. 파일을 여럿 읽어야 하거나 코드를 고치는 일은 위임한다.
2. **위임은 T3 `delegate_task`를 `mode:'async'`로 보낸다.** 보낸 뒤 바로 턴을 끝낸다.
   - 네이티브 `Agent` 도구는 쓰지 않는다. 전경 호출은 큐를 막고, 네이티브 서브에이전트는 손자를 만들 수 없다.
   - 스레드 첫 위임 전에 `orchestrator_capabilities`를 한 번 부른다.
   - `task_status` 폴링, sleep, Monitor, ScheduleWakeup으로 기다리지 않는다. 완료 알림과 도구가 주는 `next`를 따른다.
3. **위임 전에 충돌을 따진다.** 작업마다 건드릴 파일, 브랜치, DB, 외부 자원을 적어 보고 겹치면 순서를 세우거나 격리한다.
   - 같은 체크아웃을 쓰는 자식 둘이 같은 파일을 고치게 두지 않는다.
   - `isolation:'worktree'`는 프로젝트 규칙이 허락할 때만 쓴다. 새 워크트리를 먼저 제안하라는 규칙이 있으면 사용자에게 묻고 쓴다.
4. **사용자가 묻거나 결정해야 할 것은 오케스트레이터가 모아서 전달한다.** 자식의 질문이나 승인 요청이 오면 짧게 정리해 사용자에게 묻고, 답을 자식에게 넘긴다.
5. **결과를 전달할 때는 결론부터 쓴다.** 자식 스레드는 도구가 준 `link` 그대로 언급한다. 자식 보고는 사용자에게 보이지 않으니 필요한 내용은 옮겨 적는다.
6. **필요 없어진 위임은 `task_cancel`로 멈춘다.** 같은 일을 두 번 위임하지 않고, 위임한 일을 직접 하지도 않는다.
7. **리뷰와 재확인은 새 `delegate_task`로 보낸다.** 작은 리뷰 지적은 오케스트레이터가 직접 고치지 말고 원래 작업 자식이나 새 자식에게 넘긴다.
8. **눈으로 봐야 정할 수 있는 것은 오케스트레이터가 직접 보여 준다.** 스크린샷, 화면 시안, 차트처럼 보고 판단할 결정을 사용자가 자식 스레드에 들어가서 보게 하지 않는다.
   - 스크린샷 파일은 응답에 마크다운 이미지(`![설명](절대경로)`)로 넣는다. 시안 HTML은 `html_preview` 다음 `html_render`로 그린다. 경로만 적거나 말로만 설명하고 끝내지 않는다.
   - 보여 주기 전에 오케스트레이터가 먼저 파일을 열어 보고, 보고 내용과 맞는지 확인한다.
   - 그래서 화면을 다루는 위임 브리프의 완료 보고에는 스크린샷과 시안 HTML의 절대경로를 꼭 넣으라고 적는다.

## 위임 브리프 양식

자식은 오케스트레이터의 대화를 보지 못한다. 브리프에 아래를 빠짐없이 넣는다.

```
## 목표
<무엇을 끝내면 되는지 한두 문장>

## 작업 위치
- 절대경로: <경로>
- 첫 단계에서 `git rev-parse --show-toplevel`과 `git branch --show-current`로 위치를 확인하고, 다르면 멈추고 보고한다.

## 범위
- 고쳐도 되는 곳: <파일·디렉토리>
- 건드리지 말 곳: <다른 자식이 맡은 파일, 사용자 미커밋 변경 등>

## 이미 알아낸 것과 배제한 것
<오케스트레이터가 확인한 사실, 시도해서 틀린 가설>

## 제약
- 프로젝트 규칙(AGENTS.md, CLAUDE.md)을 먼저 읽고 따른다.
- 커밋은 <허용/금지>. PR 생성, push, 배포, 운영 DB 변경은 하지 않는다.
- 사용자에게 물어야 할 일이 생기면 직접 묻지 말고 질문으로 보고하고 멈춘다.

## 하위 위임
- 위임 깊이: <현재 깊이>/<한도>. 기본 한도는 3(오케스트레이터 0, 자식 1, 손자 2, 증손 3)이다.
- 서로 독립된 부분이 있거나 여러 파일을 훑어야 하면 `delegate_task`로 하위 에이전트를 만들어도 된다. 이 줄이 하위 위임 허가다.
- 하위 브리프에도 이 양식을 쓰고, 위임 깊이를 1 올려 적는다. 깊이가 한도에 닿으면 더 만들지 않고 직접 한다.
- 하위 결과를 합쳐 검증하는 책임은 위임한 쪽에 있다.

## 완료 보고
- 한 일, 바꾼 파일, 검증 결과(명령과 출력 요지), 남은 일, 사용자 결정이 필요한 것.
- 하위 에이전트를 썼다면 각각의 결과와 링크.
- 화면을 바꿨거나 시안을 만들었다면 스크린샷과 시안 HTML의 절대경로(오케스트레이터가 사용자에게 바로 보여 준다).
```

## 자식과 손자의 규칙

브리프의 "하위 위임" 절이 곧 규칙이다. 요점만 다시 적는다.

- 자식은 사용자를 직접 응대하지 않으므로 하위 결과를 기다려도 된다. 이때는 `delegate_task`의 `mode:'wait'`를 쓰거나 완료 알림을 기다린다.
- 하위 위임은 실제로 나눌 이유가 있을 때만 한다. 조회 몇 번으로 끝날 일을 떼어 주지 않는다.
- 하위 에이전트끼리도 같은 파일을 동시에 고치지 않게 위임한 쪽이 범위를 나눈다.
- 깊이 한도는 위임이 끝없이 불어나는 것을 막는 장치다. 한도를 올리려면 사용자 허락이 필요하다.

## 끝내기

사용자가 "오케스트레이터 모드 끝"처럼 말하면 일반 모드로 돌아간다. 돌고 있는 위임이 있으면 목록을 보여 주고 계속 둘지 멈출지 묻는다.
